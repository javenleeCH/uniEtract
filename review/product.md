# 产品角色评审

> 评审对象：`ux`（UniExtract）0.3.1
> 评审视角：产品 / PM —— 对开发者、CI、AI Agent 三群目标用户是否好用、完整、定位清晰

## 一句话结论

`ux` 真正成立的差异化不是「又一个 jq」，而是「**无外部依赖的确定性抽取原语**」——在「跨格式目录批量抽取」和「Agent 生成命令的确定性」两个场景它有不可替代的价值；但在「单一格式深度」和「命名 / 心智模型」上它仍像「开发者为自己写的自用工具」，且「宁可吵、不可骗」这一核心主张被 0.3.1 的输入侧 BrokenPipe 静默返回 0 直接撕裂，对主打用户（CI/Agent）是产品级硬伤，应 hotfix 而非押到 0.4.0。

## 用户画像与 JTBD

文档第一句就声明了三个目标用户（`docs/cli-design.md#L7`：软件开发者、CI 脚本、AI Agent），但三者的 JTBD 并未被对称地、一等公民式地服务，而是被压缩进「一个稳定 CLI 契约」的单一叙事里。逐群拆解：

### 1. 开发者（数据工程师 / 后端）
- **JTBD**：从日志、配置、CSV、HTML 里快速提字段，避免为每个格式手写 python/jq 脚本。
- **最痛点**：多格式混批（一个目录里 JSON+YAML+CSV+log）时，jq 只吃 JSON、xmllint 只吃 XML，得拼多个工具或写脚本。
- **解决程度**：高。`-f auto` + 目录递归 + `jq`/`xpath`/`re` 首阶段 + `--skip-incompatible` 直击这个痛点（README #L45、#L67）。
- **剩余痛点**：类型流转（`text()` 何时该插）靠经验，`-f` 显式指定是个高频陷阱（见「发现」P1-3）。

### 2. CI 脚本
- **JTBD**：把抽取结果接到流水线里，用退出码和机器可读错误做 gate / 重试。
- **最痛点**：怕「静默失败」——上游数据坏了却 rc=0，让 pipeline 绿着通过。
- **解决程度**：中。0/1/2 退出码 + `--error-format json` + `--quiet`/`--no-stdin` 方向正确（README #L106–116）。
- **致命残留痛点**：`rc=0` + stdout 空 + stderr 空**不能证明输入被完整读取**（README #L157、#L235），输入侧 BrokenPipe 被静默判成功——这恰好打在 CI 最怕的「静默丢数据」上。详见 P0-1。

### 3. AI Agent
- **JTBD**：作为 LLM 的可执行原语，生成命令后能自我校验（先看输入集、看结构化错误、看退出码），避免「幻觉式零结果」。
- **最痛点**：命令（尤其 XPath/DSL）写错了却静默零匹配，Agent 无法自查。
- **解决程度**：中高。`--list` 预演 + `--error-format json` + 决策表（README #L135–157）+ 随仓库分发 skill（README #L251–310）是同类工具里少见的「Agent 原生」投入，值得肯定。
- **剩余痛点**：Agent 最需要的「**结果 schema 校验**」被明确列入不做清单（`docs/cli-design.md#L21`），而这是 Agent 判断「抽对没抽对」的最后一公里缺口。详见 P1-1。

**结论**：三者里 CI/Agent 是当前投入与卖点最重的（契约、skill、诊断占了 README 一半篇幅），开发者反而是被「顺带」服务的。但产品口号（`docs/cli-design.md#L11`「宁可吵，不可骗」）与 CI/Agent 的实际信任度之间存在一条被文档如实承认、却未及时修复的裂缝，这是当前最大不一致。

## 差异化与定位

### 独特价值成立的部分（应强化此定位）
| 场景 | 为什么 `ux` 明显更优 | 证据 |
|---|---|---|
| **跨格式目录批量抽取** | 单二进制吃 9 类格式 + 目录发现 + `--skip-incompatible`，替代「jq+grep+xmllint+自写 python」的拼装 | README #L45、#L72 |
| **Agent 确定性抽取** | `--list` 预演输入集、结构化 JSON 诊断、0/1/2 退出码、`--no-stdin` 防挂起，Agent 能自检 | README #L135–157；`src/lib.rs#L80–102` |
| **带溯源的批量提取** | `--with-source` 的 `{path,line,record,captures}` 可与 `--list` 直接对账（正斜杠一致），定位「这条值来自哪个文件哪一行」 | README #L76；`src/model.rs#L113–141` |
| **Windows 无 jq 依赖** | 纯 Rust、无外部 C 库，WSL/Git Bash/CI runner 不必装 jq | README #L3、#L7–14 |

### 「又一个工具」的场景（应克制宣传，不要冒充替代品）
| 场景 | 为什么弱于专用工具 |
|---|---|
| 纯 JSON 精加工 | jq 只兼容「实测过的函数/轴」（`docs/cli-design.md#L20`），无人会为一个不完整 jq 换工具 |
| 纯文本 awk/sed/grep | `regex` crate 无 lookaround、无回溯引用（README #L225、#L110），正则能力弱于 pcregrep/ripgrep |
| 关系运算（join/跨文件关联/schema） | 明确不做（`docs/cli-design.md#L21`），此时必然退回 python/pandas |

**定位建议**：`ux` 的 slogan 应从「把 jq、XPath、正则放进一条记录流」（README #L3，偏「能」）前移为「**一条命令、一个二进制、确定性可对账的本地抽取，为 Agent 与 CI 而生**」（偏「稳/可信」）。30 秒示例（README #L21）第一条是 `jq(.id)`，会把新用户的第一印象导向「jq 替代品」这个它并不擅长的位置。

## 发现

### P0-1 「宁可吵，不可骗」被输入侧 BrokenPipe 静默成功破坏，且已发布仍押到 0.4.0
- **问题描述**：产品核心主张是「错误必须可观测，限制触顶报错而非静默截断」（`docs/cli-design.md#L11`）。但当前实现按**错误变体**而非 I/O 方向判 BrokenPipe，输入侧管道破裂（上游提前关闭）会被当作「正常终止」退出 0 且不写任何诊断。
- **证据**：
  - `README.md#L104`：`AppError::Io(BrokenPipe)` 一律视为正常终止并退出 0。
  - `README.md#L147–157`：`rc=0 且 stdout 为空` 的决策表自认「**或**输入侧管道破裂被静默判为成功」。
  - `README.md#L235`（已知限制）：「**退出码 0 不证明输入被完整读取**…按输入/输出侧区分已列入 0.4.0 必修项」。
  - `CHANGELOG.md#L58–60`：明确这是「甲方技术复核增列」，且**0.3.1 未改 I/O 代码**、留到 0.4.0，理由是「避免把当前行为固化为长期契约」。
- **影响**：对 CI/Agent 这是最痛的一次背叛——`cat 坏数据 | ux --quiet ... | 下游` 在最常见的管道场景下，上游提前断开会得到 `rc=0 + 空 stdout + 空 stderr`，**与「真零匹配」完全不可区分**。一个把「退出码稳定契约」当卖点的工具，在「完整性退出码」这个最关键的位上存在已知盲区，且被默认为 0。
- **建议**：不要在 0.4.0 一次大版本里才「闭环」，而应作为 **0.3.x 的 hotfix**（这是修复一个会静默丢数据的行为，属于 bug 而非 feature）。理由与「宁可吵不可骗」一致：宁可在 0.3.x 改退出码造成一次破坏性变更，也不应让主打用户在 0.4.0 之前持续踩「可信退出码不可信」的坑。同时把「管道输入 + `--quiet`」组合在 README 契约表里显式标红为「不建议用于完整性判断」，而不只是在 157 行用一段长文兜底。

### P1-1 schema 校验被列进「不做」，是 Agent/CI 数据质量场景最重要的缺失
- **问题描述**：`docs/cli-design.md#L21` 把「schema 校验」与 join、跨文件关联一起归入「单记录流模型，不做关系运算」——这个归类把「**单条记录的 schema 校验**」（纯局部、与关系运算无关）和「跨文件 join」（真关系运算）混为一谈，误伤了前者。
- **证据**：`docs/cli-design.md#L15–24` 的「不做」表；`.agents/skills/ux-extract/SKILL.md#L60` 也把「不要发明 … 提取提示、capture injection」作为 hard rule，但没有给 Agent 提供「结果是否符合预期结构」的校验手段。
- **影响**：Agent 抽取后的自检目前只能靠「非空 + 无 eval 错误」，无法回答「抽出的字段类型/必填字段是否对」。这是 Agent 从「能抽」到「抽得可信」的最后一公里。对 CI 的 data-quality gate 同理。
- **建议**：至少提供一个轻量、局部、非关系化的 `--schema`（或一个 `check(FILTER)` 之类的终阶段，断言每条记录满足某 jq 谓词，否则 `eval`/`limit` 式报错退出 1），不触碰「不做跨文件 join」的边界。优先级高于 `--path-regex`（见 P1-4）。

### P1-2 「无结果排序」伤害时间戳目录这一 `--path-spec` 主打场景
- **问题描述**：`--path-spec` 的定位就是「路径带语义」的场景（README #L7 举例时间戳目录挑 NativeHeap dump），但结果/文件顺序只按**归一化相对路径字典序**，不支持按 captures（如 `ts`、`seq`）排序。
- **证据**：`README.md#L234`（已知限制）自认「不做基于 captures 的排序，也不提供 `--sort`」；`docs/cli-design.md#L23`「排序由输入发现顺序决定」。
- **影响**：字典序对 `ts=2026-01-02` 这类 ISO 日期恰好有序，但对 `mins=2`/`mins=10`、或 `seq=9`/`seq=10` 这类**数字排序**会错序（`10 < 2`）。用户从时间戳目录按「最早→最晚」串行分析时，要么退回去自写排序，要么容忍错序。
- **建议**：0.4.0 的「captures 求值注入」（README #L244）落地后，顺带提供 `--sort-by <capture>`（数值/字符串两种语义，显式指定），这是 `--path-spec` 主用例的直接补全，价值大于「`--path-regex`/`--root` 与 `--path-spec` 并存」这类同质扩展。

### P1-3 命名与心智模型：`-f`/`-O`、`text()`/`attr()` 与目标用户已有词汇冲突
- **问题描述**：目标用户（会 jq / XPath / curl）带着既有心智进来，会撞上四处词汇重载。
- **证据**：
  - `-f`=输入格式、`-O`=输出模式（`src/cli.rs#L27、#L31`）。但 jq 的 `-f` 是「filter from file」、curl 的 `-O` 是「remote name」、绝大多数工具的 `-o` 是「output」。`-f`（输入）与 `-O`（输出）两个短旗都与其在别处的语义相反/近似。
  - `text()`（任意值 → string-value）与 XPath 的 `text()`（文本节点测试）同名不同义；`attr("href")` 与 XPath 的 `@href` 缩写对应（README #L56–60）。
  - `-f text`（输入文本）、`text()`（阶段）、`-O text`（输出文本）三者都叫「text」，沿着一行命令会出现 `ux -f text -O text -e 'text()'`（CASES #L10）。
- **影响**：学习成本里最陡的其实不是 DSL（那是可记的），而是这些「你以为懂、其实不是」的旗语义。对 LLM Agent 尤甚：向量/自回归生成时 `-f`/`-O` 极易被按 jq/curl 惯性写错。
- **建议**：短旗保留兼容，但 `--help` 与 README 把长旗作为第一推荐（`--format`/`--output`），并用一条「与 jq 的差异」对照表一次性讲清（jq 用户迁移的 5 个 differ）。`text()` 可以考虑文档里改名解释为「string-value()」，避免与 XPath `text()` 混读；若 0.5 引入新阶段更名，用别名过渡。

### P1-4 输入选择机制已膨胀到「四套并存」，0.4.0 再加一套，学习负担失控
- **问题描述**：选输入现有：位置参数 PATH、目录递归、`GLOB`、`--path-spec`（结构化段匹配）。0.4.0 已定稿再新增 `--path-regex` / `--root` 且「与 `--path-spec` 并存，不替换」（README #L243）。
- **证据**：`README.md#L74`（四种入口）、`#L81–98`（path-spec）、`#L243`（0.4.0 并存的 path-regex/root）；`docs/cli-design.md#L24` 还明确「不做跨段通配与自动 `**`」。
- **影响**：新人/Agent 面对「我该用 glob、path-spec 还是 path-regex」没有决策树，反而因「段级剪枝」「只在遍历中筛选」等差异容易用错（path-spec 目录尾不追加 `**` 的坑，README #L92）。每加一种方言，确定性卖点就稀释一分。
- **建议**：`--path-regex`/`--root` 落地时必须同时交付一张「**选型决策表**」（glob=名称通配、path-spec=路径结构带语义捕获且要剪枝、path-regex=需要跨段/全路径正则）。否则宁可不做 `--path-regex`，把精力投给 P1-1/P1-2 这类补真实能力缺口的项。

### P2-1 产品名/仓库标识不统一且撞「UX」，传播成本高
- **证据**：二进制 `ux`、crate `uniextract`（`docs/cli-design.md#L30`）、GitHub repo `uniEtract`（README #L261 的下载 URL）、文档标题「ux — UniExtract」（README #L1）四个标识并存；`ux` 与「user experience」强撞词，搜索/知识库检索噪声大。
- **影响**：低技术风险，但社交媒体/搜索引擎/package registry 的 discoverability 差，Agent 记忆里「ux」易与 UX 设计语境混淆。
- **建议**：统一对外产品名为 `uniextract`（二进制可保留 `ux` 短名 + 别名 `uniextract`），repo 名规范化小写；短期不动代码，但文档与 Release 正文统一措辞。

### P2-2 输出只有三态，缺 CSV/TSV 与「raw 字符串无引号」之外的表格化出口
- **证据**：`-O` 只有 `jsonl|text|json`（README #L75）；CSV/TSV 只作为**输入**（README #L72）不是输出。
- **影响**：「工程师抽表喂 Excel/下游 pandas」时，`-O jsonl` 还需再转 CSV；字段带逗号/引号的转义又得重做一遍。
- **建议**：列入 backlog（非 0.4.0 硬性）、优先级低于 P1-1；提供 `-O csv`（表头=对象键并集/首记录键）即可覆盖多数场景。

### P2-3 `--list` 清单不带 `-f` 格式信息，Agent 对账仍需二次猜测
- **证据**：`--list` 只输出 `{type,path[,captures]}`（`src/lib.rs#L85–97`、README #L112），不含探测出的输入格式；而 `-f auto` 对无扩展名 JSONL 会误判（README #L229、CASES #L26–27）。
- **影响**：Agent 预演后仍无法从清单确定「这个文件会被当什么格式解析」，不得不再跑一次才知 `invalid JSON`（rc=1）。
- **建议**：`--list` 输出项里追加 `"format": "<探测结果>"` 字段（或 `--list --format` 可选），把「格式误判」从运行期错误提前到预演期可视化。字段只追加不重命名，符合既有契约（README #L133）。

## 建议更改或移除的设计（可挑战现状）

### 保留（理由充分，不建议动）
- **唯一稳定契约 = CLI、不承诺库 API**（`docs/cli-design.md#L9`、ADR A1）：收敛契约面让内部可自由重构，对「脚本直接调二进制」的目标用户是正确取舍。反对把 `run()` 公有化。
- **单记录流 + 统一 `Item` 做组合而不做子命令矩阵**（`docs/cli-design.md#L161`、ADR A2）：这是与「jq|grep|xmllint 拼装」的关键差异，保留。
- **限制触顶即报错、`-O json` 失败 `abandon()` 不吐残缺数组**（ADR A5）：与「宁可吵不可骗」一致，保留，且这是好设计。
- **输出顺序 = 发现顺序（字典序）、串行、字节级稳定**（ADR 相关；`docs/cli-design.md#L18` 并发不做的理由）：理由诚实且对诊断定位成立，保留「不做并发」。
- **`slurp()`/`-O json` 保留不废弃**（README #L245）：聚合是真实需求，保留是对的。
- **captures 默认只读、不隐式注入记录流**（ADR B4）：来源元数据与记录数据分离，求值不随 spec 变化，正确。0.4.0 的「显式 opt-in 注入」是合理演进而非推翻。

### 更改
- **输入侧 BrokenPipe 的退出码语义**：从「按错误变体一律 0」改为「按 I/O 方向区分」，且**提前到 0.3.x hotfix**（见 P0-1）。这是对 ADR A3「退出码稳定」的修补而非破坏——修的是「稳定地错」。
- **「不做 schema 校验」的归类**：把「单条记录 schema 校验」从「不做关系运算」里拆出来，作为独立的 backlog 项重新评估（见 P1-1）。当前归类在概念上不成立：校验单条记录不涉及任何跨记录关系。
- **`--path-regex`/`--root` 与 `--path-spec` 并存**：方向可保留，但必须附带「选型决策表」，否则暂停该扩展、把投入转给 schema/排序（见 P1-2、P1-4）。
- **文档三次「text」重载**：在阶段表与 `--help` 里给 `text()` 加「string-value」标注，降低与 `-f text`/`-O text` 的读混。

### 移除 / 降级
- **README 与 `--help` 的「ROADMAP」段把合作方的「乙方/甲方复核」叙事写入面向用户的手册**（CHANGELOG #L60「甲方技术复核增列」可留在 changelog，但 README #L249 的「甲方技术复核增列」措辞暴露内部流程）：面向用户的文档应只讲「0.4.0 会修 BrokenPipe 语义」，不出现「甲方」内部角色。低优先级。
- **`--path-spec` 的 0.3.1「移除 time:/lit:/简写」破坏性变更**（CHANGELOG #L22–23）：方向正确（显式 `re:` 更诚实），但迁移成本落在少数已用 `time:` 的用户身上且发生在 0.3.x 小版本，未来这类「砍语法」应优先走大版本或提供至少一个 minor 的共存期。此为历史决策复盘，不做改回建议，仅提示节奏策略。

## 开放问题

1. **「唯一稳定契约 = CLI」与「Agent Skill 作为一等分发物」的边界在哪？** skill 里 `references/cli-contract.md` 实质上复制并固化了 CLI 契约（`SKILL.md#L62–71`），一旦 CLI 演进，skill 与 README 和 `--help` 构成第三处需要 CI 门禁同步的契约副本——目前只有 `check_contract_docs.py` 校验 README/`--help`/docs，尚不明确是否覆盖 `.agents/skills/` 下的契约副本。谁来保证 skill 的 `cli-contract.md` 不漂移？
2. **目标用户的相对优先级是什么？** 若三者资源冲突（如 P1-1 schema 校验偏 Agent/CI，P1-2 排序偏开发者），产品演进按哪个用户群的需求排序？README 未给出「我们优先服务谁」的声明。
3. **「零匹配 = 成功（退出 0）」对 CI gate 是否总是正确默认？** 对「抽取类」任务零匹配合理；但对「数据质量类」任务，零匹配常意味着「该有的数据没了」，用户只能靠 warning 或 `--with-source` 二次判断。是否需要一个 `--require-match`（零匹配时退出 1）的可选项？
4. **输出「紧凑 JSON」的键序是隐式归一化还是保留 jq 语义？** CASES #L1228 显示 `-O json` 的 `events.jsonl`（原 `{"n":1,"level":…}`）输出为 `{"level":…,"n":1}`（字母序），但 README 未承诺键序；若未来 jq 与其他格式的键序语义不一致，会对 `--with-source` 对账/下游 diff 产生影响，建议明确。
5. **`-f auto` 是否值得为 JSONL 无扩展名做一次「保守多行校验」而非直接按 JSON 报错？** 这是唯一一个「能被工具自己大概率判断准、却选择报错让用户显式指定」的格式（README #L229）；`auto` 的定位若从「只看扩展名」升级为「扩展名优先 + 多行 JSONL 保守识别」，可省掉 P2-3 一半的 `-f` 显式指定负担。
